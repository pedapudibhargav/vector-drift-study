Vector retrieval drift under corpus growth

Dense Hit@k falls as an enterprise RAG corpus grows from 5k to 100k documents, measured with exact (brute-force) cosine search. An oracle metadata filter recovers part of the loss. The decline appears on two embedders and under several corpus-growth schedules.

This page describes revision 1 (release v2.0.0). The earlier public release (v1.0.0-artifacts) reported curves from an approximate HNSW index whose search mode was partly exact and partly approximate; those numbers are superseded. The v1 files are kept for the record and are marked below.

Research goal

Enterprise RAG systems keep adding documents. This study asks how much dense retrieval degrades when the gold answer stays in the index but the distractor corpus grows, whether the decline is a property of the embedder or of the search method, and how much a metadata filter recovers. The decline is partly expected by construction, because the added distractors can only displace gold documents; the paper reports the size and the controls.

Full method, caveats, and threats are in the paper. Reproduction steps: REPRODUCE_REVISION1.md; validation: REVISION1_VALIDATION.md.

Primary findings (exact search, n = 200)

OpenAI text-embedding-3-small, raw dense Hit@10 falls 0.795 → 0.585 from 5k to 100k documents (drop 0.210, 95% interval [0.155, 0.270]), and to 0.515 at the full pool of 184,963 documents. Amazon Titan Text Embeddings V2 falls 0.785 → 0.610 (drop 0.175, [0.125, 0.230]). The oracle metadata filter adds about +0.08 Hit@10 at 5k and 100k on OpenAI (+0.130 at the full pool).

Controls reported in the paper: exact-versus-HNSW search-mode audit, four further HNSW builds, a 400-question bank, multi-seed and alternate corpus-growth schedules, BM25 and rank-fusion baselines, 512-token chunked documents, and a two-judge label-completeness audit. Reproduce (no re-embedding required)

Steps 1–6 describe the v1 procedure; follow REPRODUCE_REVISION1.md for the revision-1 results.

Download the published Postgres dump, restore it, and re-run sweeps against frozen vectors. You do not need to re-embed 100k documents.

  1. Clone the repo and create .env from .env.example.
  2. Start Postgres + API: docker compose up -d --build vector-drift-postgres vector-drift-api
  3. Download erb_tables.dump.gz from the latest GitHub Release into data/backups/.
  4. Restore: ./scripts/erb/restore_from_backup.sh data/backups/erb_tables.dump.gz
  5. Validate: python3 scripts/erb/validate_study.py
  6. Optional OpenAI re-sweep: python /app/scripts/erb/run_scale_sweep.py --primary-questions … (v1 procedure; see REPRODUCE_REVISION1.md for the revised one). Titan tables: document_chunks_titan / vector_drift_results_titan.

Revised step-by-step: REPRODUCE_REVISION1.md (v1: REPLICATE.md).
